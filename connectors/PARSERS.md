# Parser registry

Which code turns each source into `corpus/normalized/<source>.jsonl`, and the format quirks it handles. Everything here is plain deterministic Python; re-running needs no agent:

```bash
python3 connectors/run_all.py            # every Mac connector and export, then rebuild the index
python3 connectors/run_all.py imports    # just the exports in corpus/imports/
python3 connectors/iphone.py             # the iPhone: decrypt the latest Finder backup, our phone parsers, iLEAPP, index
python3 connectors/rebuild.py            # recompute every source from what's on disk (no downloads/decryption), then index
```

**What stays out of the corpus, and only this:** data that would compromise privacy or security (passwords, keychain,
cookies, tokens, SIM and subscriber identifiers, Siri voice samples, Wallet barcodes), other people's data (Venmo's
public feed, strangers' Bluetooth devices, suggested people), corrupted data (e.g. a 72,722-steps-in-6-minutes glitch)
and stores with nothing about the person (app configuration). Lossy or noisy isn't a reason: raw Health samples sit
next to the daily summaries, spam and deleted mail are kept with `meta.tier`, phone internals with `meta.tier =
"device"`. True duplicates are merged, not dropped. Every exclusion is counted: per source in the manifest's `notes`,
iLEAPP artifacts in `_ileapp_left_out`, export files no parser read in `_imports_unclaimed`.

Siri voice samples and Wallet barcodes are out for good, not pending: neither is needed (decided 2026-10-09).

Exports in `corpus/imports/` are complete snapshots, so their sources are rebuilt from scratch on every run. Local sources that delete their own history (screen time, Chrome, calls, Claude Code) instead keep records from earlier runs the source no longer has (`Writer(accumulate=True)`), except what a source says is no longer its own (`Writer(forget=...)`: the tabs open on another device then, documents that turned out not to be yours, Do It for Me's Claude Code sessions). The manifest and every state file are written whole or not at all (`common.write_atomic`); one cut short by a crash is read as empty (`common.read_json`). Half an emoji (a lone surrogate) is written as U+FFFD instead of failing its source.

Each run also stamps `corpus/manifest.json` with the exact parser (`file:function`) and the git commit it ran from, plus any connector files edited since that commit, so every source can be traced to the code that produced it. Commit parser changes before a run you want to keep.

## Exports dropped into `corpus/imports/` (all in `imports.py`)

`imports.entries()` walks loose files, zips and zips inside zips; each parser below gets every entry and claims the ones it understands. Unclaimed document files fall through to `other_documents`. A tar export (GitHub's `.tar.gz`) is unpacked once into `corpus/raw/unpacked/<id>/` and read from there while it's unchanged; its copy goes when it does. Two exports of one service (a second Takeout, a Discord package downloaded again, a chat exported twice) are both read, and what they share is kept once.

Zips as they come (`common.py`'s zip helpers, which `bridge.py identify` uses too; `tests/test_import_archives.py`): a member's name is read as its zip meant it (`member_name`: Archive Utility's UTF-8 without the flag that says so, Windows' backslashes, a leading `./`; a name in the DOS code page, or one zipfile can't know, as read), and one with `..`, an absolute path or a drive is skipped; `__MACOSX/`, `._*` and `.DS_Store` aren't data (`junk_member`); the same name twice is the last one, as unzipping leaves it. Zips in zips are opened 3 deep, without all of one in memory (`open_nested`: one stored as it is in place, a packed one over 64 MB from an unnamed copy in `corpus/raw/`, gone once read). Left out, said once per archive and listed in `_imports_unclaimed` with `left_out` (why), never read: a member locked with a password or packed in a way Python can't unpack (Windows' Deflate64, WinZip's AES: unzip it in Finder and drop the folder), one that unpacks to over 100 times its packed size and past 256 MB (a zip bomb), zips inside a download that unpack to over 4 times its size, a tar whose headers say it unpacks to over 100 times its size (checked header by header, before anything is unpacked) or to more than the disk has free, and a file still being downloaded (`.crdownload`, `.part`, Safari's `.download` folder). A zip that can't be opened at all (cut short) is said too.

### Mappings the app ships (`desktop/data/mappings/<slug>.json`)

A service added from the hub (or found in your data) whose slug has a mapping here is read with it, as data: no
parser code (`main.ts useLibraryMapping`; one added before its mapping shipped is read again with it at the next
launch). The rows a mapping doesn't name still go to `<folder>_other` and `<folder>_files`. Besides the keys any

## Format quirks the parsers rely on

Found on real exports in Oct 2026. If an export stops parsing, check these first. Takeout in other languages, My Activity
pages, Maps before 2023, the iPhone's Timeline, Keep's pages and Fit come from open-source Takeout parsers' fixtures and
Google's schema pages (Oct 2026), not from an export here; `tests/test_takeout_formats.py` has them made up.

**Google Takeout**
- The download page's "Part N" doesn't match the file name: Part 2 was `takeout-…-4-001.zip`. One product can fill a zip by itself (all of Mail was one 7 GB mbox in one zip).
- My Activity and YouTube history come as HTML unless JSON is asked for; both are read. JSON is better: its `time` is UTC to the millisecond. A page's time is written for people, in the account's language and zone (`Jan 13, 2024, 6:57:09 PM PST`, `13.01.2024, 18:57:09 MEZ`, older ones with no zone at all): `loose_time` reads it, a zone it doesn't know (or none) as this Mac's clock. One item is an `outer-cell`: its product in the header cell, then in the first content cell the title and its link, a channel and its link, the time, and for Gemini the answer; Products / Details under `<b>` names in the caption cell.
- Takeout names folders, files, CSV columns, titles and Gmail's labels in the account's language (German: `Meine Aktivitäten/`, `YouTube und YouTube Music/Verlauf/Wiedergabeverlauf.html`, `Abos/Abos.csv`, `Maps (Meine Orte)/`, `Gespeichert/`, `Aufgaben/`, `Google Fotos/`, `Gmail/`, `Archiv_Übersicht.html`; Spanish: `Mi actividad/`, `YouTube y YouTube Music/` with a no-break space). JSON keys stay English. So a file the name checks miss is told by what's in it (`sniffed`: `[{"header"…` is My Activity, an `outer-cell` page too, `"Browser History"`, `tasks#taskLists`, `semanticSegments` / `timelineObjects`, GeoJSON in a Maps folder), and a title in another language ("Has visto …") by its link: a search's query, a YouTube video watched.
- One file a reader fails on (damaged, or a shape not seen before) is said (`couldn't read …`) and left unread, so the catch-alls and the ledger have it; the rest of the Takeout is read. A zip part that can't be opened (a download cut short) is said too.
- An item whose `details` say "From Google Ads" is an ad you were shown (a YouTube ad, a sponsored result): kept as `kind: "ad"` (`meta.shown_as`: what it would have been), not as a watch, search or visit, and left out of the stream. So is every export's `ad`, `advertiser`, `inference` and `off_platform` (stream.py `DROP_KINDS`; Explore's year doesn't count them either): what a service showed you or decided about you, not something you did.
- Gmail: Spam and Trash are kept, tagged `meta.tier` from the `X-Gmail-Labels` header (a list, a label with a comma in it in quotes; in another language the whole list is one RFC 2047 word, `=?UTF-8?Q?Messages_envoy=C3=A9s,Important?=`, and Gmail's own labels are in that language: `SENT_LABELS`, `TRASH_LABELS`); a mail counts as sent by me if it's labeled Sent or comes from an address in `identity.json`. Takeout's separator is `From 1610964845928120745@xxx Fri Sep 07 15:56:38 +0000 2018` and bodies are mboxrd-quoted (`>From`, `>>From`); other mbox writers don't quote, so only a line like a separator starts a message. A mail without a Date is dated by its first Received line; headers in raw 8-bit that aren't UTF-8 are read as Windows Latin-1, and a part in a charset Python doesn't know keeps its text.
- Keep writes every note twice (`.json` and `.html`); only the JSON is used, unless there's no JSON (before 2018): then the page (`.heading` its date, `.title`, `.content`). Takeout's index page at its top (`archive_browser.html`) is skipped. Archive Utility unzips a second part beside the first as `Takeout 2/`: read as the same Takeout.
- Google Chat: `created_date` looks like `Wednesday, June 8, 2016 at 3:55:41 AM UTC` with a narrow no-break space (U+202F) before AM/PM (`Tuesday, 7 February 2021 at 17:13:43 UTC` in British English; other languages by `loose_time`). An attachment's `export_name` differs from the file on disk: `?` is written as `_`, and repeated names in a conversation become `X.jpg`, `X(1).jpg`, `X(2).jpg` (taken to be in message order). Attachments are copied as-is to `corpus/media/google_chat/<people> [<id>]/` and listed in `meta.files`.
- YouTube's own files are CSVs. Text cells (`Comment Text`, `Live Chat Text`) are JSON segments, `{"text": …}` each, written one after another without a list's brackets: a mention or a link to a moment of a video is a segment of its own (`mention`, `videoLink`). `yt_text` joins their text. Times are ISO with an offset and two to six fraction digits.
- Comments and playlists name videos only by id. A title comes from the watch history in the same Takeout (`YT_TITLES`) or from your uploads, else the record says "A video (<id>)": nothing is looked up online, so most of Watch later (not watched yet) has no title.
- `playlists/playlists.csv` lists every playlist, Watch later and Favorites too; each one's videos are in `playlists/<title>-videos.csv` (`Video ID`, `Playlist Video Creation Timestamp`). Before 2023 a playlist was one `<title>.csv`: its details, a blank line, then `Video Id,Time Added` (read too, not seen in a real export).
- Tasks: `Tasks.json` is `{"kind": "tasks#taskLists", "items": [lists, each with its tasks in "items"]}`. A task has `created`, `updated`, `status` (`needsAction` / `completed`), `completed`; the time it's set for is `due`, or `scheduled_time` (`[{"current", "start"}]`) in newer ones.
- Chrome's `Bookmarks.html` and `Reading List.html` are Netscape bookmark files: folders as `<H3>` names each followed by a `<DL>`, `ADD_DATE` in Unix seconds (`0` when there's none). Before, they were imported as a single page each.
- Saved (Maps lists and saved links) isn't in an export here yet. Read as Google documents it: one `Saved/<list>.csv` per list with `Title,Note,URL,Tags,Comment` and no dates.
- Maps (your places) is GeoJSON, coordinates `[lon, lat]`; a place Maps no longer has is at `[0, 0]` (no place), named from its link's `?q=` when it has no name. Before 2023: `Google Maps URL`, `Published`, `Title`, `Location` (`Address`, `Business Name`, `Geo Coordinates`), and a review's `Star Rating` and `Review Comment`.
- Location History: Takeout's Semantic Location History (`Semantic Location History/2019/2019_JANUARY.json`, English even in a German Takeout, its top folder `Standortverlauf/` or `Location History (Timeline)/`) has `placeVisit` and `activitySegment`, times as `startTimestamp` or, before 2022, `startTimestampMs` (text). The phone's Timeline export (2024 on): Android's `{"semanticSegments": […]}` with `latLng` "52.52°, 13.40°"; the iPhone's a list, every value text (`"0.85"`), places `geo:52.52,13.40`, `placeID`.
- Fit's workouts (`Fit/All Sessions/*.json`) and its data by device are kept by the catch-all, which otherwise leaves out files named for sessions and devices; `.tcx` files are listed as not read.
- Fitbit (`Fitbit/`, `Google Health/` since the rename) isn't read with the Fitbit mapping: that's for a Fitbit download in a folder of its own. Its `Global Export Data/` has the archive's files side by side (exercise, sleep, weight, resting heart rate: the catch-all keeps a record each) and the JSON series by the minute; `Physical Activity_GoogleData/` has Google's CSVs of the same and more, a readme beside each family; the older folders (`Oxygen Saturation (SpO2)/`, `Heart Rate Variability/`, `Temperature/`, `Active Zone Minutes (AZM)/`) theirs. `fitbit_days` reads every series by the reading a record a day, on the clock of `Your Profile/Profile.csv`'s zone; their daily files (`daily_*.csv`, `Daily SpO2 - …`, `Computed Temperature - …`), `Health Fitness Data_GoogleData/` (sleeps, exercises: a row each) goes to the catch-all; the routes (`gps_location_*.csv`) are a record each, named by the workout they're in.

**vCards**
- vCard 3.0 with folded lines and grouped properties (`item1.TEL`). `contacts.Resolver` reads every `.vcf` in `corpus/imports/` (loose files first, then inside zips) before the Mac's AddressBook, so phone exports win; it decodes them as the importer does (`contacts.vcard_text`).
- Google's export escapes a URL's colon (`item1.URL:http\://…`) and writes `BDAY:--1212` without a year; iCloud's repeats `type=` and writes `BDAY;X-APPLE-OMIT-YEAR=1604:1604-12-12`; Android's 2.1 writes `N;CHARSET=UTF-8;ENCODING=QUOTED-PRINTABLE:` and a photo as indented base64 ended by a blank line; Address Book 4 (Mac OS X 10.4) wrote cards with anything but ASCII in UTF-16BE with no byte order mark and CR line ends.

**LinkedIn**
- Files now carry a member id (`Shares_<member id>.csv`); it's stripped before matching names.
- `Connections.csv` starts with a `Notes:` preamble before the header row (a quoted paragraph and a blank line, with Windows line ends in some downloads); older exports have none, and no URL column. Headers are in English whatever the account's language.
- `Ad_Targeting.csv` repeats column names, so it's read with `csv.reader`, not `DictReader`.
- Date formats differ by file: `Jul 2025`, `2025/09/16 21:54:21 UTC`, `9/3/26, 7:30 PM`, `Tue Sep 22 00:27:49 UTC 2026`, `2026-09-22 13:39:25`.
- The "complete" archive has no `messages.csv` when there are no messages, and downloads named `….zip.zip`.

**Meta (Instagram, Facebook)**
- Accounts Center exports Instagram and Facebook separately unless both profiles are linked there. Choose JSON (default is HTML), All time (Facebook defaults to Last year), Higher media quality, and the notify address (it defaulted to an old work email). "Start export" asks for the password again, and the download link expires 4 days after it's ready.
- All text is UTF-8 that was decoded as latin-1 (`â¦` for `…`); `fix_meta` re-encodes it one character at a time, so text cut off mid-character keeps the rest and text that's already right (the encrypted-chats download) is left alone.
- Times are `timestamp_ms`, or `timestamp` in seconds (milliseconds in the encrypted-chats download), sometimes text: `meta_time` tells them apart by size.
- A deleted account is "Facebook user" / "Instagram User" in every chat it was in; it's never taken for you (`META_NOBODY`). Without identity.json, you are whoever is in the most chats.
- Two zips (two accounts, or two downloads) have the same paths inside: each is read (`done` is by export and path). A broken or empty file is left unread, so `_imports_unclaimed` lists it. HTML exports are kept as `imported_documents`, not read as messages.
- Two layouts in one export: newer files are lists of `{timestamp, media, label_values: [{label, value | href | timestamp_value | media | dict | vec}]}`, older ones use `string_map_data` / `string_list_data`. `meta_item` flattens either into label/value pairs.
- Messenger: threads sit in `messages/{inbox,filtered_threads,message_requests,e2ee_cutover}/`. Chats that became end-to-end encrypted (Messenger's default since late 2023) are not in the export; `e2ee_cutover/` holds only their history from before the switch, so Messenger volume collapses after 2023 (10k messages in 2022, 52 in 2026). The rest is in Messenger → Settings → End-to-end encrypted chats → Message storage → Download secure storage data.
- Facebook's older files use plain items (`{"name": …, "timestamp": …}`); `meta_item` keeps their text fields too, plain-name lists (a post's tags) and `*_timestamp` times. `meta_items` reads every list in a file, one level down too (`event_responses_v2` > `events_joined`, `events_declined`, each item saying which), and a list of plain names (`ads_interests`' `topics_v2`) as an item each. `META_SKIP` drops Facebook's own suggestions (people you may know, suggested friends).
- Media `uri`s are relative to the export root (`your_instagram_activity/messages/inbox/<thread>/photos/<id>.jpg`, `media/posts/…`); files are copied to `corpus/media/<instagram|facebook>/<uri>`.
- A message's `reactions` are `{actor, reaction, timestamp}` (Instagram leaves out `timestamp` on older ones; the emoji is double-encoded like all text). `call_duration` is in seconds, 0 for a call nobody answered. `share` has any of `link`, `share_text` (the shared post's caption), `original_content_owner`. Facebook marks a message taken back with `is_unsent`. A message with none of content, link or media (a caption-only share, an unsent one) is kept as `[shared: …]` / `[unsent]`.

**X**
- `tweets.js` cuts a long post at 280 characters. `note-tweet.js` has the whole text but no link to its post: they're matched by the second they were made and how the text starts (`x_note_for`). A long post with no short copy is kept as its own post (`note:<id>`).
- `deleted-tweets.js` is shaped like `tweets.js`, plus `deleted_at`; kept as posts with `meta.deleted`. `deleted-tweet-headers.js` (ids and times only) is left to the catch-all.
- `grok-chat-item.js`: one item per turn, `{chatId, createdAt, sender: {name: User | Agent}, message, grokMode}`. Chats have no title, so each is named by its first prompt.
- A group DM's name is a `conversationNameUpdate` among its messages (`{name, initiatingUserId, createdAt}`); the last one names the thread. One-on-one DMs keep the conversation id as their name.
- `full_text` writes `&`, `<`, `>` as `&amp;` `&lt;` `&gt;` and links as `t.co`: the text is unescaped and each link replaced with its `entities.urls` / `entities.media` `expanded_url` (DMs: `urls[].expanded`). A retweet is `RT @name: …` (`meta.retweet_of`).
- An edited post is a post per version, `edit_info` naming every version (`initial.editTweetIds`, or `edit.initialTweetId` with `editControlInitial`): each is kept; the earlier ones have `meta.replaced_by` and `meta.tier` superseded, the later `meta.edit_of`.
- Before 2018 ("Grailbird"): `data/js/tweets/YYYY_MM.js` (`Grailbird.data.tweets_YYYY_MM = […]`, `text` not `full_text`, times `2012-01-31 23:59:59 +0000`, a retweet's whole text in `retweeted_status`) and the same tweets again in `tweets.csv`, kept once. Media folders have been `tweet_media` and `tweets_media`, plus `deleted_tweets_media`, `community_tweet_media`, `direct_messages(_group)_media`.
- `account.js` says whose archive it is (`accountId`); one that doesn't fails the archive, rather than every DM being taken for someone else's. Any other file that's cut short or damaged is listed as not read, and the rest is read.

**Spotify** (no real export here yet: documented formats)
- Account data and Extended streaming history are two requests, and arrive separately (both often named `my_spotify_data.zip`). Account data's own plays (`StreamingHistory*.json`) cover only the last year, and are in Extended history too (to the second, not the minute): up to Extended history's last play, they're read from it only.
- Extended history was `endsong_N.json` (with `username`, `ip_addr_decrypted`, `user_agent_decrypted`) before 2023, `Streaming_History_Audio_<years>_N.json` and `Streaming_History_Video_<years>.json` since; Account data's plays were `StreamingHistoryN.json` (podcasts in it look like songs), and are `StreamingHistory_music_N.json` and `_podcast_N.json` (`podcastName`, `episodeName`) since. A podcast's episode is by its show (`meta.show`), not an artist, so it isn't counted as a song; `meta.what` is song, episode or audiobook.
- Extended history: `ip_addr` and device fields stay out; `conn_country`, `reason_end`, `shuffle`, `incognito_mode` are kept in meta. An audiobook play has `audiobook_title` and `audiobook_chapter_title` and no track name; it has no artist, so Explore's Listening doesn't count it as a song.
- `Playlist*.json`: `{"playlists": [{name, lastModifiedDate, items: [{track | episode | audiobook | localTrack, addedDate}]}]}`; playlists have no id. `SearchQueries.json`'s `searchTime` ends in `[UTC]`. `Inferences.json` is a list of ad segments: `3P_…` from Spotify's data partners, `1P_…` its own; `Marquee.json` is each artist's listener segment for you (artists buy Marquee ads by it). Both are kind `inference`, for What They Know.

**Reddit** (no real export here yet: documented formats)
- `comments.csv` is `id, permalink, date, ip, subreddit, gildings, [gildings_silver, gildings_supergold,] link, parent, body, media`; `posts.csv` `id, permalink, date, ip, subreddit, gildings, title, url, body`; `messages_archive.csv` (messages.csv before) `id, permalink, thread_id, date, ip, from, to, subject, body`, its links written `https:/www…` and names `u/…` or `/u/…`; `drafts.csv` dates its rows `created`. Dates are `2026-03-09 15:59:23 UTC`. A row cut short (fewer fields than the header) is read with what it has. A post to your profile is in subreddit `u_<you>` (thread `u/<you>`).
- `chat_history.csv` (`message_id, created_at, username, message, channel_url, channel_name, conversation_type, …`) has both sides of Reddit Chat; a chat without a `channel_name` is named after the others in it. When who you are names none of its usernames, the one name every chat has is the export's owner, yours. `post_votes.csv` / `comment_votes.csv` are `id, permalink, direction` (up, down, none); `saved_posts.csv` / `saved_comments.csv` are `id, permalink`; `subscribed_subreddits.csv` is `subreddit`. None of these carry dates. A link's subreddit and title come from its permalink.

**WhatsApp exported chats** (no real export here yet: documented formats, from open-source parsers' fixtures)
- iPhone: `[1/2/24, 3:04:05 PM] Name: text`, a narrow no-break space before AM/PM, an LRM before the line and the text of WhatsApp's own lines and media (`Name: <LRM>image omitted`, `<LRM><attached: 00000012-PHOTO-….jpg>`); its own lines go under the chat's (or group's) name. Android: `1/2/24, 3:04 PM - Name: text`, its own lines with no name (`1/2/24, 3:04 PM - Bea added you`), media `<Media omitted>` or `IMG-20240102-WA0001.jpg (file attached)`. Other languages write their own placeholders (`<Medien ausgeschlossen>`, `imagen omitida`), kept as written.
- A short chat, or one whose first message is long, is still a chat when it's named as an export is (`_chat.txt`, a name with WhatsApp in it) and starts with a message. Slack's one-member text export (`[2020-04-20 13:47:27] <jjordan> text`) is not taken for one.

**Slack** (no real export here yet: documented formats)
- Free and Pro exports have public channels only; Business+ (on request) and Enterprise have every conversation. Enterprise Grid's names people in `org_users.json`; how an org-wide export lays out its workspaces isn't documented, so the nearest folder up with a list (and the nearest with people) is taken as the export's. One member's export (an org owner's) comes as text (`channels/`, `dms/`, `files/`) or JSON (`channels/`); how its times are zoned isn't documented (taken as UTC). slackdump's own dump (`C123.json`, `{channel_id, messages}`) isn't read as messages: the catch-all keeps each.

**Claude.ai** (no real export here yet: documented formats)
- A message's `attachments` carry `extracted_content`: a paste's or a file's text. It's kept with the message, up to 20,000 characters each (`ATTACHMENT_CAP`); `files` (images) have only a name.
- A message's `text` has a placeholder ("This block is not supported on your current device yet") where an artifact or a tool's use was; its `content` blocks have them (`text`, `tool_use` with `input`, `tool_result`, `thinking`). The text is made from the blocks: an artifact's content (`[artifact: fib.py]`), a tool's use by name (`[web_search: …]`); tool results and thinking stay out.
- Since 2026 projects come as `projects/<uuid>.json`, one project each, and `memories.json` (`[{conversations_memory, project_memories: {project uuid: text}, memory_files: [{path, content, updated_at}], account_uuid}]`) is what Claude remembers: a `note` each, by claude.ai, not yours. Big accounts get `…-batch-0000.zip`, `…-batch-0001.zip`, each read.
- `projects.json`: `[{uuid, name, description, prompt_template (its instructions), is_starter_project, created_at, docs: [{filename, content, created_at}]}]`. The starter project claude.ai gives everyone is kept, as not yours. A `projects.json` or `conversations.json` that isn't JSON (some other app's, in a Drive folder) is passed over.

**ChatGPT** (no real export here yet: documented formats)
- A conversation is a tree (`mapping`: nodes with `parent`, `children`, `message`); `current_node` ends the branch on screen. An edited prompt or a regenerated answer starts another branch: those turns are kept too, with `meta.tier` superseded. With no `current_node` (or one not in the tree) the branch that ends last is the one on screen; a loop in the tree stops where it comes round.
- `content_type`: `text` and `multimodal_text` have `parts` (strings; an image is `[image]`, a voice message its `audio_transcription`), `code` and `execution_output` have `text`, `tether_quote` a page's `title`, `text`, `url`. `thoughts` and `reasoning_recap` (the model's thinking) and turns hidden from the chat (`metadata.is_visually_hidden_from_conversation`) stay out, but for the custom instructions (`user_editable_context`) and memory (`model_editable_context`) hidden at a conversation's start: a `note` each, once. A tool's turns are kept for code output, quotes and images it made. Files attached are named from `metadata.attachments`. A turn without a `create_time` has its conversation's.
- `user.json`, `shared_conversations.json`, `message_feedback.json` and `model_comparisons.json` are left to the catch-all.

**Discord**
- The package arrived within hours, not the 30 days Discord quotes.
- The data package holds only messages you sent (DMs, group DMs, server channels). Categories are chosen at request time (Account, Messages, Servers used here).
- `Messages/index.json` names many DMs `"None"` or `Direct Message with Unknown Participant`; those are named from the friends list in `Account/user.json`. Recipients who aren't friends stay as user ids. `Attachments` are CDN links, kept as text (they may have expired).
- A package downloaded again is saved as `package (1).zip`, which sorts before `package.zip`: every package's `messages.json` of a channel is read, ids keep each message once.
- Before late 2021 folders were lowercase and a channel's had no `c` (`messages/<id>/`); before 2024 messages were `messages.csv` (`ID,Timestamp,Contents,Attachments`, times with `+00:00`) and a channel's `type` a number (1 DM, 3 group DM, 0 a server's); since, `messages.json` with times in UTC written without a zone (read as UTC). Since mid-2025 some packages name their folders in the account's language: a folder holding `<id>/channel.json` is read as Messages, `user.json` beside it as Account. A server's channel the index doesn't name is `<channel> in <server>`; a DM with someone not on the friends list is named by their id. `Activity/` (analytics, JSON lines, often GBs) isn't read and is listed as such.

**Notion (Export all workspace content)**
- Markdown & CSV, with "Create folders for subpages". Files sit under `Export-<uuid>/<section>/` (sections such as Private & Shared, and one per teamspace); each page is `<Title> <32-hex page id>.md`, its subpages in a folder named after it, and each database is written twice (`X <id>.csv` and `X <id>_all.csv`; only `_all` is kept).
- Pages carry no dates and every zip entry is stamped with the export time. Only database rows have `Created time` / `Last edited time` lines, so most pages come out undated (`meta.ts_from` is empty). The parser deliberately doesn't borrow dates from the local Notion cache: each parser reads only its own export, and joining sources is a separate step.
- Links between pages are URL-encoded relative paths (`Trip%20Ideas/…md`); they're reduced to the linked page's title, and links to other files resolve to attachments.
- A big workspace's download is one zip holding `Export-<uuid>-Part-1.zip`, `-Part-2.zip` …: a page, its subpages and their files can be in different parts, so pages and files are found by their place inside the export, whichever part they're in. A subpage's folder is named with its page's id or without it. A workspace exported twice is read once (page ids). Property times (`Created: January 1, 2024 10:00 AM`) are this Mac's clock, kept in UTC.
- The HTML export: `<Title> <id>.html` pages (`h1.page-title`, properties in `table.properties`, `@`-prefixed times) are read as pages too; its `index.html` is a list of them.

**iPhone backups (Finder, encrypted)**
- Ticking "Encrypt local backup" starts a backup at once, even with the iCloud option still selected. A backup that ends without `Info.plist` is incomplete: Manage Backups lists it as "Unknown, 12/31/00".
- Decryption (iOS 10.2+): PBKDF2-SHA256 (DPSL, DPIC = 10M rounds) then PBKDF2-SHA1 (SALT, ITER) unwraps the class keys in `BackupKeyBag`; `Manifest.db` and each file are AES-256-CBC with a zero IV; per-file keys sit in the `Files.file` NSKeyedArchiver plist. Uses the `cryptography` package, already on this Mac.
- A file is stored at `<backup>/<id[:2]>/<id>` with `id = sha1("<domain>-<relativePath>")`, so files can be located without decrypting the manifest. That's how the needed ones were staged where a terminal without Full Disk Access could read them.
- Don't cut decrypted files to the manifest's `Size`. It's read when the backup starts, and files that grow during the backup are stored in full: 167 files here, mostly the X app's DM databases, up to 2 MB longer. Strip the PKCS7 padding instead. iLEAPP's own iTunes reader has this bug, which is why it runs on our mirror.
- The keychain (`KeychainDomain`) holds saved website, Wi-Fi and mail passwords that unlock with the backup password. It's never decrypted.
- The phone's `sms.db` has the same schema as the Mac's `chat.db` and the same message guids. Same for `CallHistory.storedata` (`ZUNIQUE_ID`).
- The phone's Photos.sqlite is the same iCloud library as the Mac's (matched by `ZCLOUDASSETGUID`), so it isn't parsed again. The backup holds no photo originals when iCloud Photos is on, only thumbnails.
- Opening a mirror database with a writable SQLite connection changes the file (checkpoint, vacuum). Read-only connections are safe but create empty `-wal`/`-shm` files next to it.
- Finder backs up into the device's folder in place: while it runs, and after it's cut off, `Status.plist` `SnapshotState` isn't "finished" and the folder is part old, part new. A first backup cut off has no `Info.plist`. iOS 9 and earlier backups have `Manifest.mbdb`, not `Manifest.db`.
- iOS 10.0 and 10.1: the keybag has no DPSL/DPIC (one PBKDF2-SHA1 round) and `Manifest.db` isn't encrypted (no `ManifestKey`); both came with 10.2.
- Unencrypted backups leave out Health, call history, Safari history, Wi-Fi and the keychain by design. So only an encrypted backup's file list says what the phone no longer has; after an unencrypted one only stale `-wal`/`-shm` files are taken out of the mirror (a newer database beside an older log reads as a corrupt one).

**Apple Health (`healthdb_secure.sqlite`)**
- Only encrypted backups include Health. Samples are `samples` (data_type, start/end in Apple-epoch seconds) → `objects` (provenance) → `data_provenances` (`tz_name`, `origin_product_type`, `source_id`); values are in `quantity_samples` or `category_samples`. App names (`sources`) live in the other file, `healthdb.sqlite`.
- Data types are bare numbers. Mapped here by units and typical values: 7 steps, 8 distance (m), 12 flights, 10 active kcal, 9 resting kcal, 5 heart rate (per second, ×60), 61 respiratory rate (per second), 173 headphone dB, 187 walking speed, 188 step length, 182 double support, 194 walking asymmetry, 63 sleep (0 in bed, 1 asleep, 2 awake, 3 core, 4 deep, 5 REM), 2 height, 3 weight. Unmapped types are counted in the manifest notes.
- `objects.type` 2 = a deleted sample with no value. Eight Sleep deletes and rewrites thousands on every sync.
- Exact duplicate samples are common (6.5k here): Eight Sleep writes each sleep stage twice per sync and re-syncs nights, and step samples were duplicated around a phone switch. Without dedup, nights add up to 30+ h of sleep.
- Glitches exist: one 2019 sample said 72,722 steps and 40 km in six minutes. Samples over 250 steps, 400 m or 20 flights per minute are dropped.
- Each phone counts its own steps. When two phones overlap (old and new phone in the same pocket), take the larger total per day, never the sum.
- Each sample's own `tz_name` gives local days with no other source. Sleep sessions are samples within 2 h of each other.
